# Audit Captivia — 2026-08-09

Audit complet du code source (whitebox), backend NestJS + Prisma, frontend Next.js 16.
Périmètre : dépendances, secrets, configuration, auth, autorisation, logique métier, injections, exposition.

**Points forts constatés** : ValidationPipe strict (whitelist + forbidNonWhitelisted), contrôle d'ownership systématique (helper `ensureAnimalOwnership`), tokens de reset robustes (32 octets, 1h, single-use), messages d'erreur uniformes (pas d'oracle email), aucun `.env`/secret committé, JWT_SECRET requis au démarrage (Joi + garde), bcrypt cost 10, pas de SQL brut ni d'exécution de commandes, frontend sans `dangerouslySetInnerHTML` ni secret `NEXT_PUBLIC_`.

## Findings

### HIGH

**H1 — Bypass total du paywall : l'abonnement premium est un mock**
`backend/src/subscription/subscription.service.ts:39` — `POST /users/me/subscription` met `isPremium: true` en base sans aucun paiement. Le commentaire le dit : « Mock upgrade: set user as premium. Replace with Stripe Checkout session in production ». N'importe quel compte gratuit active instantanément : animaux illimités, carnet de santé, QR codes premium.
→ *Correction* : intégrer un vrai paiement (Stripe/Paddle) ou, à défaut, un flag d'activation administré ; ne jamais exposer un endpoint d'auto-upgrade.

**H2 — Dépendances : 48 vulnérabilités backend (2 critical), 17 frontend (12 high)**
`npm audit` :
- **Backend (directes, runtime)** : `axios` (SSRF via NO_PROXY bypass, high), `@nestjs/core` (injection, high), `nodemailer` (SMTP command injection, high — fix 9.0.5, semver major), `prisma` (high), `@nestjs/common`/`config` (moderate). Critical : `@xhmikosr/decompress`, `handlebars` (chaîne dev via `@swc/cli`/`@nestjs/cli`).
- **Frontend (directes)** : `next` 16.1.6 → **HTTP request smuggling dans les rewrites** (fix 16.3.0, non-breaking), `next-intl` (open redirect), `sharp` (4 CVE libvips, fixable via next 16.3.0).
→ *Correction* : `npm audit fix` dans les deux projets puis `npm audit fix --force` après revue (nodemailer 9, @swc/cli 0.8.1).

### MEDIUM

**M1 — Aucun rate limiting sur l'authentification**
`RateLimitGuard` n'est appliqué qu'à wikipedia/wikidata/gateway/species. `POST /auth/login`, `/auth/register`, `/auth/forgot-password` sont illimités → brute-force de mots de passe, création de comptes en masse, spam de mails de reset.
→ *Correction* : appliquer un throttler strict sur `/auth/*` (ex. 5-10 essais/min/IP+email, lockout progressif).

**M2 — Rate limit contournable par spoofing X-Forwarded-For**
`backend/src/common/guards/rate-limit.guard.ts:96` — `getClientIp()` prend la **première** valeur du header `x-forwarded-for` envoyé par le client. Un attaquant change le header à chaque requête et vide les 100 points/min.
→ *Correction* : ne lire que le dernier hop (ou configurer le proxy pour écraser XFF) ; utiliser `req.ip` avec `trust proxy` correctement configuré.

**M3 — DoS par amplification sur `/gateway/search`**
`backend/src/gateway/api-gateway.service.ts:122` — une seule requête `search` déclenche jusqu'à **100 espèces GBIF × 2 fetchs externes** (Wikipedia + Wikidata) = ~200 requêtes sortantes + travail CPU, sans borne sur le travail effectué (le paramètre `limit` n'est pas appliqué à l'enrichissement). Combiné avec M2, c'est un vecteur de DoS contre le serveur et les APIs tierces.
→ *Correction* : borner le nombre d'enrichissements (max 10), rendre l'enrichissement optionnel, rate limiter plus sévèrement.

**M4 — Premium accordé à l'email opérateur sans vérification d'appartenance**
`backend/src/auth/auth.service.ts:21` — `effectivePremium()` donne le statut premium à tout compte dont l'email figure dans `OPERATOR_EMAILS`. Comme l'inscription ne vérifie pas la possession de l'email (aucune confirmation), un attaquant qui s'inscrit avec l'email d'un opérateur **avant** que ce compte n'existe obtient le statut opérateur.
→ *Correction* : confirmation d'email à l'inscription ; ou créer les comptes opérateurs en seed et empêcher l'inscription sur ces emails tant qu'ils ne sont pas confirmés.

**M5 — CORS `*` + credentials**
`backend/src/main.ts:12` — `origin: process.env.CORS_ORIGIN || '*'` avec `credentials: true`. En prod sans `CORS_ORIGIN` défini, l'API accepte toute origine. Pas d'impact immédiat (auth par header Bearer, pas de cookies) mais config dangereuse si l'app évolue ; et `CORS_ORIGIN` n'est documenté dans aucun `.env.example`.
→ *Correction* : définir `CORS_ORIGIN` à l'origine exacte du frontend en prod ; retirer `credentials` si inutile.

**M6 — Pas de headers de sécurité (Helmet)**
Aucun `helmet` : pas de CSP, `X-Content-Type-Options`, `X-Frame-Options`, HSTS sur l'API. Standard pour toute API NestJS exposée.
→ *Correction* : `app.use(helmet())` (+ CSP adapté).

### LOW

**L1 — Endpoints d'administration accessibles à tout compte authentifié**
`/database/stats`, `/errors/recent`, `/monitoring/metrics`, `/analytics/*` ne sont protégés que par `JwtAuthGuard` (n'importe quel compte gratuit). Pas de rôle admin. Les journaux d'erreurs peuvent contenir des détails internes.
→ *Correction* : rôle `admin` + garde dédiée (ex. `@Roles('admin')`).

**L2 — `/api/open-data/*` sans rate limiting (proxy vers APIs tierces)**
`backend/src/external/open-data.controller.ts` — endpoints publics non protégés par `RateLimitGuard` (contrairement à wikipedia/wikidata/gateway) → abus/amplification vers iNaturalist, EOL, Wikidata.
→ *Correction* : ajouter `RateLimitGuard`.

**L3 — QR public : `baseUrl` non validé + incohérence opérateur**
`backend/src/animals/animals.service.ts:144` — (a) le paramètre `baseUrl` n'est pas validé (URL arbitraire possible dans le QR) ; (b) le check premium utilise `user.isPremium` au lieu de `effectivePremium` → un opérateur légitime ne peut pas générer de QR alors qu'il est premium partout ailleurs.
→ *Correction* : allowlist de domaines pour `baseUrl` ; réutiliser `effectivePremium`.

**L4 — Page publique du QR expose les notes privées + historique de santé complet**
`backend/src/animals/public-animal.controller.ts` — quiconque scanne le QR (slug 16 chars, non devinable, mais imprimé sur l'animal) voit `notes` du propriétaire et tout le carnet de santé. Choix produit assumé, mais à confirmer consciemment.
→ *Option* : restreindre les champs (ex. masquer les notes).

### INFO

- **I1** — Token JWT stocké en `localStorage` (`frontend/src/lib/api-client.ts:40`) : volable par XSS. Aucun XSS trouvé aujourd'hui, mais cookie HttpOnly + SameSite=Strict serait plus robuste.
- **I2** — `frontend/src/app/api/mobile-link/route.ts` renvoie l'IP LAN du serveur (disclosure mineure en prod).
- **I3** — `docker-compose.yml` : `POSTGRES_PASSWORD: password` en clair (dev uniquement, à ne pas copier en prod).
- **I4** — `getApiBase()` construit `http://${host}:3001` côté navigateur : en déploiement HTTPS, les appels API en HTTP clair seraient bloqués (mixed content) et le token transiterait en clair si jamais servi ainsi → prévoir un reverse proxy TLS devant le backend.

## Actions recommandées (ordre)

1. **Bloquer l'auto-upgrade premium** (H1) avant toute mise en prod.
2. `npm audit fix` backend + frontend, vérifier `next@16.3.0` (H2).
3. Rate limiting sur `/auth/*` + correction XFF (M1, M2).
4. Borner l'enrichissement de `/gateway/search` (M3).
5. Confirmation d'email à l'inscription (M4).
6. CORS strict + Helmet (M5, M6).
7. RBAC admin sur les endpoints d'administration (L1).

Rien de compromis aujourd'hui : pas d'injection, pas de fuite cross-user (BOLA systématiquement contrôlé), pas de secret exposé. Les risques majeurs sont métier (paywall) et de dépendances.
